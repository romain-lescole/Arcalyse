Arcalyse — your Capella model, inside and out

Standalone application (a single HTML file) to explore, analyse, check and export a Capella / ARCADIA model without opening Capella. The .capella file is read locally in the browser: no data is sent anywhere.

Open a model

  1. Drag and drop a .capella file anywhere in the window, or click 📂 Browse… on the start screen (or 🔷 CAPELLA in the toolbar).
  2. The model is parsed, then the 🔷 Capella Data view opens automatically.
  3. To switch models, simply drop another file.

Only the semantic .capella file is read. .aird (diagrams) and .afm files are rejected: they do not contain the model elements.

The three modes

🗺 Relation MapInteractive graph centred on an element and its neighbours, filterable by types and relations.
📊 Table ViewTable of every element in the file, with computed columns (Metachain).
🔷 Capella DataDedicated analysis views: tree, cards, table, links, chains, interfaces, ports, index.

Save and share

💾 HTML page saves the whole application with the model embedded. When that file is opened, the model reloads by itself: handy to freeze a state or share an analysis with someone who does not have Capella.

Security and offline operation

No network connection is required or used. All resources are embedded in the file, including the graphics library D3.js v7.9.0 (ISC licence). No cookies, no browser storage, no tracking, no data upload. Exports (PDF, ZIP, PNG, SVG, CSV, HTML) are generated in the browser without any external library, and the HTML reports produced are standalone too. A saved 💾 HTML page remains usable offline.

Showing a chain in the graph

Click a chain (⚡) in the tree, or the 🗺 button of the ⚡ Chains view: the Relation Map switches to chain view, which shows the full graph — several inputs, several outputs, branches and loops — laid out in layers according to the chosen layout (→ LR, ↓ TB, ← RL). Blue edge = carried by an actor, green = by the system, grey = unallocated; INPUT / OUTPUT badge; edges labelled with the exchange. A banner summarises the chain; ✕ Leave chain, a double-click on a node or a click in the tree return to the Relation Map.

Reading the graph

Hovering a node keeps its direct neighbours highlighted and fades the rest. Each node's header shows the readable name of its type. The Element types panel only lists types present in the tree, sorted by ARCADIA layer, with their element count.

ARCADIA colours

Detail panel

Clicking a name (almost anywhere) opens the detail panel: Human Type and description, attributes, outgoing references, incoming references (what points to this element?), owner and owned elements. Everything is clickable to navigate step by step.

⚡ Chains

FunctionalChain, OperationalProcess and PhysicalPath are rebuilt as a graph: several inputs, several outputs, branches and loops are preserved.

Filters and sub-views

Filter by type and by layer (OA, SA, LA, PA, EPBS). ▦ Diagrams: one card per chain. 🗺 Relation Map view: interactive graph (LR / TB / RL / radial / zigzag layouts, ⬡ Compact, ✂ Names) and injection into the main Relation Map.

Card content

  • Top-down diagram, Capella style: blue carried by an actor, green carried by the system, grey unallocated; thick border = input or output.
  • Involved functions: flow order, type, allocating component, input/output role, number of incoming/outgoing exchanges.
  • Involved Functional Exchanges: numbered source → target, Exchange Items, carrying Component Exchange. For a physical path: components, Physical Links and allocated CEs.
  • Buttons 🖼 PNG · 📐 SVG · 📋 Copy (paste into Word/PowerPoint) · ⬇ CSV.

🔌 Interfaces & ports

Three complementary views, from functional to physical. Each offers Row / Component views, a component × component ▦ N² matrix (click a cell = list of exchanges) and a 🩺 Checks report.

HTML exports (🔀 and 🔌): ⬇ HTML = the displayed view; ⬇ HTML (all views) = tabbed report Row view / Component view / Matrix / Checks, with current filters, search and clickable matrix. Files are standalone and use the current theme colours.

🔀 Component Exchange

Orientation of ComponentPorts: UNSET (attribute absent) · IN · OUT · ⇄ INOUT. The actual direction is deduced from both ports:

→ Oriented / ← ReversedAn IN or OUT port imposes the direction (source → target or the opposite).
⇄ BidirectionalINOUT port(s) with no other constraint.
? Not orientedTwo UNSET ports: unknown direction (dotted line).
⚠ InconsistentOUT→OUT or IN→IN — except for a DELEGATION, where the direction is deduced from parent / child nesting.

Each exchange shows its kind (ASSEMBLY, DELEGATION, FLOW), its allocated FEs (ƒ), its Exchange Items (▤) and its carrying Physical Links (🔌). Checks: CEs without FE, orphan ports, inconsistent orientations, non-oriented CEs, PA-layer CEs not allocated to a physical link.

🔌 Physical Link

Links between physical components (and actors) through their PhysicalPorts. For each link: the allocated Component Exchanges (⇢) and, on each port, an n CP badge giving the allocated Component Ports. Filters with / without CE. Checks: links without CE, physical ports not connected or without Component Port, unallocated PA-layer CEs.

🧩 Ports

Function Port ↔ Component Port ↔ Physical Port traceability, rebuilt from PortAllocation and ComponentPortAllocation.

≡ TraceabilityOne row per Function Port / Component Port with FE, CE, physical ports and links. Layer and text filters, “incomplete chains”. CSV export.
▣ By componentPhysical ports → carried Component Ports; Component Ports ← allocated Function Ports.
🩺 ChecksUnallocated ports at each level; inconsistent direction between function port and component port; FE ↔ CE alignment (the FE's ports must be allocated to the ports of the CE carrying it) and CE ↔ PL (same with physical ports). Delegations are followed step by step.

Results are kept in memory; ↻ Recompute refreshes them. Checks are only computed when the 🩺 Checks tab is opened.

Cross-cutting analyses computed from what the open model contains: a section absent from the model (no state machine, no capabilities…) is simply reported as empty, and checks only cover practices actually used.

🧪 Use case — reviewing a Capella model

  1. Load the .capella file (drag and drop). Check 📖 Type index to see the model's composition.
  2. Browse with ▦ Cards and 🌳 Tree; open the detail panel to follow incoming and outgoing references.
  3. Analyse a neighbourhood in 🗺 Relation Map: pick a component in the tree, adjust depth, layout and criteria.
  4. Review the chains in ⚡ Chains: inputs/outputs, unallocated functions (grey), exchanges without carrying CE.
  5. Check the interfaces: 🔀 Component Exchange (N² matrix, CEs without FE, orientations), 🔌 Physical Link (links without CE), 🧩 Ports (FE ↔ CE ↔ PL alignment).
  6. Measure maturity in 🔬 Analyses: traceability coverage between layers, uncovered capabilities, incomplete state machines; compare with the previous version of the model to prepare a review.
  7. Produce a deliverable: chain PDFs with appendices, CSV of checks and tables, HTML reports; or 💾 HTML page to share the whole analysis.
