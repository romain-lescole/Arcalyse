📖 Help — Relation Map · Capella

Arcalyse — your Capella model, inside and out

Standalone application (a single HTML file) to explore, analyse, check and export a Capella / ARCADIA model without opening Capella. The .capella file is read locally in the browser.

Opening a model

  1. Drag and drop a .capella file anywhere in the window, or click 📂 Browse… on the home screen (or 📁 File › 🔷 Open a Capella model).
  2. The model is analysed, then the 🧭 Explorer › ▦ Cards view opens automatically.
  3. To change model, simply drop another file (it replaces the displayed model).
  4. For a new version of the same model: 📁 File › 🔄 Load a model update shows the delta first, then updates after confirmation (see 🔄 Watch).

First time? On the home screen, 🚀 Getting started shows where to open your file, then resumes once the model is loaded to show where to find the help and tutorials. ? Help ▾ › 🎓 Guided tour presents each area of the interface step by step (more complete with a loaded model). In each view, ? Help ▾ › 🎯 Tour of this view presents its menus and what they do.

Only the semantic .capella file is read. .aird (diagrams) and .afm files are refused: they do not contain the model elements.

The main areas

🗺 Relation MapInteractive graph centred on an element and its neighbours, filterable by types and relations.
▤ TableAll model elements in a table: view tabs, attribute, relation and path columns, sort, filters, CSV export.
🔷 Capella viewsDedicated analysis views: explorer (tree, cards, index), links, chains, interfaces, ports, index.

Saving and sharing

⚠ When a model is loaded, the browser asks for confirmation before leaving the page (← Back button, closing the tab): otherwise the work in progress would be lost. Remember to 💾 Save.

💾 Save (Ctrl+S) writes the page directly to a file chosen once, then overwrites it at each save, without going through downloads (Edge / Chrome; elsewhere, the page is downloaded). Shift+click or Ctrl+Shift+S: save as. 💾 HTML page downloads the page. In both cases, the whole application is saved with the embedded model. When this file is opened, the model reloads by itself: handy to freeze a state or share an analysis with someone who does not have Capella.

The saved page contains: the model, the view bar (menus, pins), the dashboards, the ▤ Table tabs and columns (path columns, filters, widths, sort), the theme and the naming rules. Not kept: the version loaded for ⚖ Comparison and the filters of the other views.

📁 File › ⚙ Save the interface and views: the same settings without the model, in a .json file (parts of your choice); ⚙ Load an interface and views applies them again, for example with another model or a new version of the page.

Offline operation

The application works without a connection: all resources are embedded in the file, including the D3.js v7.9.0 graphics library (ISC licence). Exports (PDF, ZIP, PNG, SVG, CSV, HTML) are generated in the browser, without any external library, and the HTML reports produced are standalone too. A saved 💾 HTML page remains usable offline.

Showing a chain in the graph

Click a chain (⚡) in the tree, or the 🗺 button of the ⚡ Chains view: the Relation Map switches to chain view, which shows the complete graph — several inputs, several outputs, branches and loops — arranged in layers according to the chosen layout (→ LR, ↓ TB, ← RL). Blue edging = carried by an actor, green = by the system, grey = unallocated; INPUT / OUTPUT badge; edges labelled with the exchange. A banner summarises the chain; ✕ Leave chain, a double-click on a node or a click in the tree go back to the Relation Map.

Reading the graph

Hovering a node: its direct neighbours stay highlighted, the rest fades. Each node's banner carries the readable name of its type. The Element types panel only lists the types present in the tree, sorted by ARCADIA layer, with their number of elements.

▤ Table

Table of all the model elements, one per row, opened with the ▤ Table button of the bar. Rows follow the types checked in the sidebar (expanded layers); a double-click on a row opens the detail panel. No global search or layer filter here: each column's Filter… fields replace them.

View tabs

Each tab keeps its own view: checked element types, 🎯 scope (independent of the other views and tabs), displayed columns and their order, filters, widths and sort. A new tab has no type checked: check those to list in the sidebar. + adds a tab (copy of the columns of the displayed view, no type checked), double-click renames it, ✕ closes it. Tabs are saved with the 💾 HTML page and in the ⚙ interface file.

✨ Path column (metachain)

Adds a computed column which, for each element of the table, follows a path of relations in the model and shows what it finds at the end. Examples: the functions allocated to each component, the components connected to a component through its ports, the name of the package owning a requirement.

Building the path: choose the start type (only its rows will be filled), then, at each step, the relation to follow; the type of the next step is deduced automatically. The last step can read a value (Name, ID, attribute); otherwise, the cell shows the names of the reached elements. The choices offered depend on the loaded model:

Name · ID · Type · Human Type · attributesDisplayed value (end of the path).
Owner [Type]First owning element of the chosen type.
Owned element [Type]Directly contained elements of the chosen type (e.g. a component's ports).
Capella relationsAllocation, realization, involvement… in both directions.
attribute → TypeElement designated by an attribute (source, target, involved…).
← incoming referenceElements designating this one (reverse direction).
via [Type] → [Type]Going through an intermediate element (e.g. port → Physical Link → opposite port).

👁 Live preview: choose a sample element of the start type (🔍 filter, list, Next ▸ to go to the next element whose cell would be filled). The preview shows the elements reached at each step, the step where the path stops if it finds nothing, the final content of the cell and the number of elements for which it will be filled.

+ Add a step · ✕ deletes a step and the following ones · ✏ (⊞ Columns menu) edits an existing column · the preview updates at each change.

ƒ⇆ Functional Exchange

Exchanges between functions (all layers), same organisation as 🧱 Logical Component, with a layer filter (OA, SA, LA, PA) and an Allocation filter as in ƒ Functions (🧩 System, 👤 Actors, ∅ Unallocated; double-click: only this one) and the All allocation targets list of the layer (actors, then system and subsystems as a tree, sub-components included; in OA: operational entities and actors); in the exchange views, an exchange is kept if either of its two functions matches:

◧ Blocks viewDefault view. Each function drawn as in Capella: rounded box with the function name, green if allocated to the system, blue if allocated to an actor, grey if unallocated (or parent function); input pins (green) on the left and output pins (orange) on the right with the port name; next to each pin, the exchange and the remote function (several exchanges on the same pin: listed one below the other, centred on the pin). Click on the remote function: shows its block (changing page and relaxing filters if needed), ↩ Back returns to the starting block; click on a block title: detail panel. Pale pin: unconnected port; dotted pin: exchange connected directly to the function, without port (normal for OA activities). “with ports or exchanges” option (unchecked by default) to hide parent functions.
≡ Line viewSource function, output pin ▶ and port → exchange → input pin ▶ and port, target function; Exchange Items (▤), Component Exchanges allocating it (🔀), chains (⚡).
▣ Function viewOne card per function: received (←) and sent (→) exchanges.
▦ MatrixFunction × function (row = source, column = target), limited to 100 functions to stay responsive (the most connected); filter by layer or function to see the others.
🩺 ChecksOrphan ports, exchanges without Exchange Item, leaf functions without exchange, parent functions carrying ports, exchanges without port (except OA), LA / PA exchanges not allocated to a Component Exchange.

The Line, Function and Blocks views are paged by 100 (◀ ▶) to stay responsive on models with several thousand functions; CSV and HTML exports cover the whole filtered result.

🎬 Scenarios

Sequence diagrams of Capella scenarios — ES (Exchange Scenario), FS (Functional Scenario), OES / OAS in OA, IS (Interface Scenario) — redrawn from the .capella file alone. On the left, the list sorted by layer then by capability (layer, type filters, search); on the right, the diagram: lifelines (light blue = actor, blue = component, green = function, grey = entity), messages with, for ES, their exchange context in braces, activation bars, functions (green rectangles), states (light grey ellipses) and modes (dark grey), combined fragments (ALT, OPT, LOOP, PAR…) with their guards, “ref” references to another scenario (click: open it). Click an element: its details. Lifeline names stay visible at the top when scrolling; scrolling with the bars, the mouse wheel (Shift + wheel: horizontal) or by click-dragging the diagram background. Zoom − / +, PNG / SVG exports and image copy. 🩺 Checks: empty scenarios, messages without exchange, lifelines without represented element, scenarios outside any capability, missing references. The detail panel of a scenario or a capability also offers 🎬 to open the diagram.

The order of events is that of the model; spacing is computed (the layout drawn in Capella is in the .aird file, which is not read): the content is faithful, not the pixel position.

🔀 Behavior Exchange (formerly Component Exchange)

Scope: PA-layer Component Exchanges whose two ends are Behavior Physical Components (no Node). The number kept out of the model total is recalled at the top of the view.

Scope: exchanges between Physical Components Behavior, and between a Behavior and an actor (most often a node) connected to it; these actors appear with only their relevant ports.

◧ Blocks view (default): Physical Components Behavior drawn as in 🧱 Logical Component (blue = system, light blue = actor; UNSET / IN / OUT / INOUT ports; clickable exchanges and remote components; expandable allocated functions). The other views (Line, Component, Matrix, Checks) are unchanged.

Orientation of ComponentPorts: UNSET (attribute absent) · IN · OUT · ⇄ INOUT. The actual direction is deduced from the two ports:

→ Oriented / ← ReversedAn IN or OUT port sets the direction (source → target or the reverse).
⇄ BidirectionalINOUT port(s) with no other constraint.
? UnorientedTwo UNSET ports: unknown direction (dotted line).
⚠ InconsistentOUT→OUT or IN→IN — except for a DELEGATION, where the direction is deduced from the parent / child nesting.

Each exchange shows its kind (ASSEMBLY, DELEGATION, FLOW), its allocated FEs (ƒ), its Exchange Items (▤) and its carrying Physical Links (🔌). Checks: CE without FE, orphan ports, inconsistent orientations, unoriented CEs, PA-layer CEs not allocated to a physical link.

🔌 Physical Link

Links between physical components (and actors) through their PhysicalPorts. For each link: the allocated Component Exchanges (⇢) and, on each port, an n CP badge showing the allocated Component Ports. In the title blocks (here as in 🔀 Component Exchange), long lists are folded after 4 items: click +N others to expand them. Filters with / without CE. Checks: links without CE, physical ports not connected or without Component Port, unallocated PA-layer CEs.

◧ Blocks view (default): each node (Physical Component Node) drawn as in Capella: yellow for a system node, light blue for an actor node; physical ports as yellow squares; next to each port, the Physical Link (⇄) and the remote node, clickable to go to its block. 🧩 Ports

Function Port ↔ Component Port ↔ Physical Port traceability, rebuilt from the PortAllocations and ComponentPortAllocations.

≡ TraceabilityOne row per Function Port / Component Port with FE, CE, physical ports and links. Layer, text, “incomplete chains” filters. CSV export.

ƒ Functions and 🔬 Analyses

Results are kept in memory; ↻ Recompute refreshes them. Checks are only computed when the 🩺 Checks tab is opened.

Tables: under each header, a Filter… field per column (several words: all required; !word: exclude); the number of displayed rows is shown above, with ✕ clear. Dragging the right edge of a header sets the column width (double-click: automatic width). Filters and widths are kept when the view is redrawn. A table wider than the view has a horizontal scroll bar stuck to the bottom of the screen while it is visible (also Shift + mouse wheel).

Cross-cutting analyses computed from what the open model contains: a topic absent from the model (no state machine, no capabilities…) is simply reported as empty, and the checks only cover the practices actually used. The tabs and commands of each sub-view are framed by category (views, filters, exports), as in ƒ Functions.

ƒ Functions (first tab of 🔬 Analyses)

OA activities and SA / LA / PA functions, layer by layer, with their descriptions highlighted.

Allocation filter (🌳 Hierarchy and 📋 Table): 🧩 System 👤 Actors ∅ Unallocated, with the number of functions of each kind. Click = show / hide, double-click = only this kind (double-click again: show all). Each function carries an edging of the corresponding colour (double edging if allocated both to the system and to an actor); in the tree, parent functions kept for the hierarchy are faded. “Allocation kind” column in the table and exports.

Allocation target (list next to the filter): a specific actor, or the system and its subsystems as an indented tree (white-box LA / PA layers), with the number of functions; a subsystem includes its sub-components. ✕ removes the filter. In white box, the “Subsystem” column gives the path of the enclosing components (full path on hover).

🌳 HierarchyNumbered tree (1, 1.1, 1.2…) with badges: allocation, exchanges ⇄, realizes ⬆ / realized by ⬇, missing description. “Descriptions” option to read them in the tree. Click a function: sheet on the right (path, description, summary, sub-functions, allocation, ports, incoming and outgoing exchanges, chains, capabilities, states, traceability tree upwards and downwards). The sheet links navigate from one function or layer to another. The ⋮ separator between the tree and the sheet can be dragged to adjust the widths (double-click: default widths).
📋 TableOne row per function, indented (Flat option without indentation); resizable columns (header edge), sortable (click), filterable by text (field under the header) or by values as in Excel (▼: sort, search, check boxes with counts; a multi-value column is split) and hideable (⊞ Columns); full descriptions as an option; quick filters; number of functions shown / total. Cell selection: click-drag, Ctrl+click, Shift+click, then 📋 Copy or Ctrl+C (paste into Excel or Word; Esc clears). CSV and 🌐 HTML exports (current columns, widths, filters and sort).
⛓ TraceabilityOA → SA → LA → PA paths going through the chosen layer, with descriptions; ∅ = break.
📊 Metrics◂ collapses a layer (it moves to the left of the labels, ▸ to expand it); only expanded layers are exported: 🌐 HTML of the indicator table, high-definition 🖼 PNG or 📋 image copy for a presentation. Layer comparison: count, leaves, depth, description, allocation, exchange and traceability rates, coverage by chains and capabilities; breakdown by level; most connected functions.
✍ Name qualityOffline: verb first (infinitive in French, base form in English — built-in list of about 1,000 verbs), -ing form or action noun first, vague verbs, capital letter, spaces, punctuation, length, minority language in the layer. “Name quality” column and “Name to review” filter in the table, indicator in the metrics. ⚙ Naming rules: accepted domain verbs and false verbs, kept in the 💾 HTML page.
🩺 ChecksName quality (above), missing or too short descriptions, TODO/TBD/NOT DONE markers, duplicates, missing or multiple allocations or allocations on a parent function, leaves without exchange, exchanges on parent functions, unused ports, traceability breaks.
📄 Functional fileHTML report: one tab per layer, one numbered section per function (description, allocation, inputs / outputs, realizations, chains, capabilities), plus metrics and checks. Printable.

🔄 Watching the .capella file (updates)

The 🔄 Watch button (next to 📁 File) detects that a new version of the loaded file has been saved (by Capella) and offers to update the display. Nothing is applied without your confirmation.

DetectionAutomatic, to be checked in the 🔄 Watch menu (off by default; every 10 s, 30 s, 1 min or 5 min), when coming back to the window, or manual (🔍 Check now). A notification shows the number of elements ➕ added, ➖ deleted, ✎ modified, ↪ moved; the button badge shows the number of pending saves.
Delta🔍 View the delta: filterable list, property-by-property detail (before / after), summary by layer, CSV export, or opening in ⚖ Version comparison.
Several savesThe cumulated delta (displayed model → last save) is the one that will be applied; each detected save is also listed with its own delta (compared with the previous one). If the file goes back to the displayed version, the proposal disappears.
After the updateThe current view is kept. 🕘 Session update history (delta of each); ⚖ comparison with the version before the last update or with the opening version.
From another file📁 File › 🔄 Load a model update: choose the new file; the same delta is shown before confirmation, and this file becomes the watched one. If fewer than 50% of the elements are shared with the displayed model, a warning says it may not be the same project, and the update asks for confirmation.
BrowserEdge / Chrome: open the model through 📁 File › 🔷 Open or by drag and drop for direct access (automatic re-read). Otherwise (other browser, saved HTML page), the change is reported when possible and the file must be selected again (📂).

➕ Creation · ➖ DeletionWith the container; contained elements (ports of a deleted function…) are attached: “with 2 contained elements”.
✏ RenamingOld name → new name.
📝 DescriptionDescription or summary modified (differences in formatting only are ignored).
⚙ PropertiesAttributes (kind, nature, orientation…), property values.
🔗 LinksReferences added (+) or removed (−): allocations, realizations, Exchange Items…
↪ Move · 🔁 TypeChange of owner; change of the element type.
LevelsSummary (counts by category, layer and family) · Simple (one sentence per change) · Detailed (each property before → after) · Full (+ identifier, technical type, path).
Presets📰 Release notes (Simple) · 🔍 Review (Detailed) · 🧾 Audit (Full, technical elements not grouped).
FiltersCategories, layers, type families, search; grouping by category, layer, family or parent element. Attach technical elements to their element (checked by default): allocations, realizations, involvements… appear as 🔗 links of the element concerned rather than as separate elements.
Excluding a rowUncheck it: it stays visible (struck through) but disappears from the copy and exports; ↺ include all again.
📋 CopyCopies exactly what is displayed, in the chosen format: formatted (Word, Outlook, Teams, OneNote: headings, lists, tables), plain text, Excel table (one row per change) or Markdown.
Exports⬇ CSV, ⬇ standalone HTML, 🖨 Print (or PDF).

📑 Requirements

Requirements Viewpoint requirements (identifier, text, attributes, incoming / outgoing Capella relations and relations between requirements) and basic Capella requirements (SystemUserRequirement…, RequirementsTrace traces). Filters: family, type, attribute value, linked to the model or not.

📋 ListID, name, folder, text, attributes, linked elements (with their layer) and linked requirements.
▦ CoverageNumber of elements linked to each requirement, by ARCADIA layer.
🩺 ChecksRequirements linked to no element, without text, without identifier, duplicate identifiers, relations to a missing element; leaf functions and components without requirement (only in the layers where other elements have some).

🏷 Properties (PVMT)

Properties of the PVMT extensions (domains, groups, properties and units) and simple properties set on the elements. ○ = default value never entered.

▦ Grid by groupOne row per element, one column per group property; total of the numeric properties.
Σ SummaryBy property: sum, minimum, maximum and average of the numeric values, or breakdown of the values.
📖 DefinitionsDefined groups, classes and architectures they apply to, filled-in and missing elements.
🩺 ChecksElements targeted by a group but not filled in, values left at default, groups without a link to their definition.

🗃 Data & interfaces

📦 Exchange ItemsMechanism, elements (name: type [cardinality]), Functional / Component Exchanges carrying them, interfaces allocating them.
🔌 InterfacesAllocated Exchange Items, ports providing or requiring them, components using or implementing them.
🧱 Classes & typesClasses (typed properties), enumerations (literals), physical quantities (unit), inheritance and uses; predefined types as an option.
🩺 ChecksExchange Items not carried or without content, Functional Exchanges without Exchange Item, empty or unused interfaces, Exchange Items of an FE missing from the interfaces of the carrying CE's ports, types never used.

⛓ Constraints

All the constraints: role (guard, pre / post-condition), expression (text links are replaced by the name of the cited element), language, constrained elements, owner. Checks: empty constraints or without expression, missing cited elements, without constrained element, duplicates.

An element's detail panel also shows its linked requirements, its properties and its constraints. The corresponding indicators are in the 📐 Dashboard catalogue.

📐 Dashboard (separate tab, next to 🔬 Analyses)

Build your own dashboards from all the computed indicators (≈ 130 on a complete model): model, functions (by layer and layer comparison, allocation, allocation targets, subsystems, naming), chains, Component Exchanges, Physical Links, ports, traceability, capabilities, modes & states, requirements, properties, data & interfaces, constraints, checks. A sample dashboard is created the first time it is displayed.

✏ EditSwitches to editing: ＋ Add an item (catalogue with search and collapsible categories, “Layout” first, live preview), ＋ when hovering an item to insert one before it, “＋ Add an item” tile at the end of the page, ⚙ configure, ⧉ duplicate, ✕ remove. The view keeps its scroll position during the changes.
ChartsFigure, gauge (green ≥ 90%, orange ≥ 50%, red otherwise), horizontal or vertical bars, donut, stacked or grouped bars, table, free text (titles, comments). Number of categories displayed (the rest is grouped as “Others”) and sort can be set.
LayoutDrag an item by its title to move it; bottom-right corner to resize it (snapped to the 3, 4 or 6 column grid).
Several pagesOne tab per dashboard page; the ＋ tab adds an empty page. Double-click a tab (or ✎ on the active tab) to rename it. While editing: ⧉ Duplicate, ✨ Example, 🗑 Delete. Dashboards are kept in the 💾 HTML page.
Printing🖨 Print in A4 portrait (default) or landscape format: items are redrawn at page size, in light colours, with a header (name, model, date). “Save as PDF” in the print window to get a PDF.
Exports🌐 Standalone HTML (as displayed); ⬇ / ⬆ JSON to reuse a layout on another model.

🧪 Use case — reviewing a Capella model

  1. Load the .capella file (drag and drop). Look at 🧭 Explorer › 📖 Type index to see what the model is made of.
  2. Browse with 🧭 Explorer (▦ Cards and 🌳 Tree); open the detail panel to follow incoming and outgoing references.
  3. Analyse a neighbourhood in 🗺 Relation Map: choose a component in the tree, set depth, layout and criteria.
  4. Review the chains in ⚡ Chains: inputs/outputs, unallocated functions (grey), exchanges without carrying CE.
  5. Check the interfaces: 🧱 System / Logical Component (Capella-style blocks with ports, orphan or unoriented ports), 🔀 Behavior Exchange (PA), ƒ⇆ Functional Exchange (functions as Capella-style blocks with pins, orphan ports, exchanges without Exchange Item), 🔌 Physical Link (links without CE), 🧩 Ports (FE ↔ CE ↔ PL alignment).
  6. Measure maturity in 🔬 Analyses: traceability coverage between layers, uncovered capabilities, incomplete state machines; compare with the previous version of the model (⚖ 📰 Release notes or 🔍 Review report, to copy into Word or Outlook) to prepare a review.
  7. Produce a deliverable: PDF of the chains with appendices, CSV of the checks and tables, HTML reports; or 💾 HTML page to share the whole analysis.
